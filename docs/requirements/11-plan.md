# 開発計画

開発はP0〜P3、PX（拡張）、P4の6つのフェーズで進める。P3で成功基準の流れが通り（目標は6月中旬）、PXでマップの機能を揃える（目標は8月上旬、G-13、G-18）。P4（AWS環境への移行）の時期は未定。各フェーズは完了条件（ゲート）を満たしてから次に進む。

> 図「開発フェーズ · 5フェーズと4つの完了条件」は企画書（非公開）にある。必要になったら Mermaid で描き直す。

上の図は、PXを加える前のフェーズ構成。最新の日程、機能の依存関係、Issueの一覧は別タブにある：実装計画

各フェーズの「開発期間」は、週10〜15時間のペースで換算した作業量で、P0〜P3の合計は約290〜400時間（中央は約340時間。テーマ3で追加した要件を含む）。開発に使える時間は週5〜15時間で変動する。目標はP0が1月下旬、P1（v0.1.0）が3月中旬、P2（v0.2.0）が5月上旬、P3（v0.3.0）が6月中旬、PX（v0.4.0）が8月上旬（中央の見積もり。全体の幅は6月上旬〜11月上旬、G-13、G-18）。期限は決めず、すべて作り切る（G-17）。フェーズが終わるたびに、実績で日程を見直す。

## P0 準備・設計（開発期間：約3〜4週間）

目的は、開発の土台を作り、最大のリスク（UIの作り込みとローカルLLMの性能）を早めに見極めること。作業は、リスクの検証（描画方式の試作、マップとカレンダーの間のドラッグ、ローカルLLMの比較）を先に行い、その後で基盤と仕様に進む（G-14）。試作のコードは本体に入れず、結論をADRに残す。

- [ ] GitHubリポジトリ（モノレポ）を作り、ディレクトリ構成を決める
- [ ] mainとdevelopのブランチ保護、Issue・PRのテンプレート、ラベル、Projectsのボード、マイルストーン（P0〜P4）を整える
- [ ] commitlint、pre-commit、PRタイトルとブランチ規則の検査（pr-title.yml、branch-policy.yml）を入れ、必須チェックに追加する
- [ ] Docker ComposeでAPI、ワーカー、PostgreSQL（pgvector・pg\_bigm）、Redis、Ollamaを起動する（ヘルスチェック付き）
- [ ] ci.yml、security.yml、Dependabotを整える
- [ ] otel-lgtmを起動し、APIのログ・メトリクス・トレースがGrafanaで見えることを確かめる
- [ ] Kiroを導入してデータ共有をオプトアウトし、AGENTS.md（正）、CLAUDE.md、Kiroのsteeringに規約を置く（G-10）
- [ ] FastAPI、SQLAlchemy、Strands、Ollamaで最小構成のエージェントを動かす
- [ ] Ollamaで使うLLMと埋め込みモデルを2〜3種類比較して選ぶ
- [ ] マインドマップの描画方式を試作で比較する
- [ ] Kiroでマインドマップの仕様（requirements・design・tasks）を作る
- [ ] ADR 0001〜0003、0012、0013、0015、0018を書く

成果物：リポジトリと運用ルール一式、compose.yaml、CI、監視基盤、マインドマップの仕様書、ADR 7本。

## P4 AWS環境への移行・連携拡張（開発期間：約2〜4週間、時期は未定）

対象要件：AU-05、IN-07〜10、OP-02。作業は「AWS環境への移行の手順」の手順に従い、terraform.ymlとdeploy.ymlによるCD（OIDC認証）を整え、監視の送り先をCloudWatchとX-Rayに切り替える。余力に応じてOutlook、Notion、GitHub Issuesとの連携を加える。完了条件は、AWS環境で主要シナリオのE2Eテストが通り、削除手順まで確認できていること。完了時にv1.0.0を出す。
