# 非機能要件

重視する順は、セキュリティ（外部アカウントのトークンを預かるため）、移植性（AWS環境へ移すため）、保守性の順。性能の数値は、ローカル環境での目標値（案）とする。

| ID | 区分 | 要件 | 基準・目標値（案） |
| --- | --- | --- | --- |
| NF-01 | 性能 | API応答（LLM呼び出しを除く）の95パーセンタイル | 300ミリ秒以内 |
| NF-02 | 性能 | マインドマップの操作が、ノード数が増えてももたつかない | 500ノードで、操作から画面の反応まで100ミリ秒以内（I-08） |
| NF-03 | 性能 | AIの応答は逐次表示（SSE）し、待ち時間を体感させない | 最初の文字が出るまでの時間を計測し、改善の指標にする |
| NF-04 | 起動 | 全サービスが1コマンドで起動し、ヘルスチェックで状態を確認できる | `docker compose up` で起動し、全サービスがhealthyになる |
| NF-05 | セキュリティ | パスワードは強いハッシュで保存する | Argon2idを使う |
| NF-06 | セキュリティ | アクセストークンは短命、リフレッシュトークンはローテーションと失効に対応する | アクセストークンの有効期限は15分程度 |
| NF-07 | セキュリティ | 外部サービスのOAuthトークンは暗号化して保存する | アプリの鍵で暗号化し、AWS環境ではKMSに置き換える |
| NF-08 | セキュリティ | 秘密情報をリポジトリに含めない | `.env` はGit管理外。AWS環境ではSecrets Managerなどに置き換える |
| NF-09 | セキュリティ | OWASP Top 10への対策 | SQLはORMとバインド変数、XSSはReactのエスケープ、CSRFとCORSは設定で制御する |
| NF-10 | セキュリティ | 依存ライブラリの脆弱性を検知する | Dependabot、pip-audit、npm auditをCIで回す |
| NF-11 | セキュリティ | プロンプトインジェクション対策 | 予定の本文など外部由来のテキストはデータとして扱い、指示として実行しない。書き込み系の操作は必ず承認を挟む |
| NF-12 | プライバシー | 個人データを最小限にする | AWS環境には実データを載せない。ユーザー削除時は関連データも削除する |
| NF-13 | 整合性 | 外部との同期は冪等にする | 外部IDに一意制約を付け、同じ予定を二重に登録しない |
| NF-14 | 整合性 | 非同期ジョブは再実行できる | 失敗時は指数バックオフで自動リトライし、上限を超えたら失敗として記録する |
| NF-15 | 保守性 | 外部依存はポート＆アダプターで隔離する | domain層とapplication層からFastAPI、Strands、boto3を直接importしない |
| NF-16 | 保守性 | 静的解析と型チェック | Ruff、mypy（domain層とapplication層はstrict）、ESLint、tsc |
| NF-17 | テスト | テストの層を分ける | 単体（pytest）、結合（Testcontainers）、E2E（Playwright）。外部APIは記録済みの応答で再生する |
| NF-18 | テスト | LLMの品質を回帰確認できる | 評価セット（自然文と期待する日時の組など）で、出力の形式と内容を確認する |
| NF-19 | 可観測性 | ログとトレース | JSON形式の構造化ログにリクエストIDを付ける。OpenTelemetryでトレースとメトリクスを取る（詳細は「ロギング・モニタリング基盤」の章） |
| NF-20 | 可観測性 | LLM呼び出しの記録 | 用途、モデル、入出力トークン数、所要時間を毎回記録する |
| NF-21 | 移植性 | 設定は環境変数で切り替える | `LLM_PROVIDER=ollama` を `bedrock` に変えるだけで切り替わる |
| NF-22 | コスト | ローカル開発の費用 | クラウド費用は0円。Kiroは無料枠を基本とする |
| NF-23 | 使いやすさ | 日本語UI、キーボード操作、PCの画面を優先 | スマートフォンはPWAで閲覧と軽い操作ができる |
