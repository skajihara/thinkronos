# テスト計画

テーマ7（テスト計画）の成果物。テスト戦略、品質ゲート、アクセシビリティ、AIの評価、性能の確かめ方、E2Eのシナリオの一覧をまとめる。書き方の細かい規則は実装規約のテストの章にある。

## テスト戦略（I-01）

ピラミッド型にし、DBに関わるテストは本物のPostgreSQLで行う。

| 層 | 対象 | 道具 | 方針 | 量 |
| --- | --- | --- | --- | --- |
| 単体 | domain層とapplication層（操作の適用、循環の検出、空き時間の計算など）、フロントのロジック | pytest、Vitest | ポートを偽物に差し替え、外部に触れない | 最も多い |
| 結合 | adapters層（リポジトリ、RLS、制約、マイグレーション、外部APIのアダプター） | pytest、Testcontainers | 本物のPostgreSQLとRedis。テーブルの所有者ではないロールで接続する。外部APIは記録した応答を再生する | 中くらい |
| 認可 | ワークスペースのデータを扱うすべてのAPI | pytest、Testcontainers | 別のワークスペースのデータを読めず、書き換えられないこと | APIごとに1本以上 |
| 整合性 | 操作ログとスナップショット | pytest | スナップショットとその後の操作を再生した結果が、nodesと一致すること（D-12） | 操作の種類ごと |
| E2E | 主要なシナリオ | Playwright | LLMはモック、外部サービスはスタブに差し替える | 下の一覧 |
| AIの評価 | AI機能 | tests/eval（ローカル） | モデルやプロンプトを変えたときに流す | 機能ごとに20件前後 |
| 性質ベース | マップの操作の不変条件（循環ができない、兄弟の並び順が重ならない、操作の再生結果が状態と一致する、項目単位の後勝ち） | Kiroの正しさの確認（Correctness）、pytest | Kiroの仕様で性質を定め、ランダムな操作の列で確かめる（G-20） | 不変条件ごとに1本以上 |

## 品質ゲート（I-02、I-07）

| いつ | 何を確かめるか | 通らなければ |
| --- | --- | --- |
| PRごと（必須チェック） | Lint、型チェック、単体、結合、ノード編集のIMEのテスト（CDPで変換中を再現）、変更した行のカバレッジ80%以上、ビルド、セキュリティ（重大度High以上）、スモークE2E（P1のIssue 1-4以降） | マージできない |
| 毎晩 | すべてのE2Eと、その中のアクセシビリティの自動検査 | Slackに通知し、翌日の最初に直す |
| リリースの前（フェーズの終わり） | 性能の計測、キーボードだけでの操作の手動確認、実機の日本語IME（Microsoft IME）でのノード編集の手動確認、AIの評価セット | リリースしない |

## アクセシビリティ（B-07、I-06）

- 目標はWCAG 2.2のAA相当。ライトとダークの両方に対応する。
- E2Eの中でaxe-coreの自動検査を行い、重大な違反があれば失敗にする。
- 自動検査では拾えない問題が残るため、リリースの前に、キーボードだけで主要な操作ができるかを手で確かめる。
- 自由に配置できるマップのキャンバスは、キーボード操作（MM-06）とアウトライン表示（MM-16）を代わりの手段にする。

## AIの評価（E-03）

合格基準は機械的に確かめられる指標にする。内容の良さは、人による3段階の評価と、実際の採用率で追う。採用率は、提案した件数を分母に、操作ログで出どころがAIの操作を数えて出す（D-15）。

| 機能 | 合格基準（機械的に確かめる） | 追う指標 |
| --- | --- | --- |
| 子ノードの提案（AI-01） | 出力の形式が正しい割合100%。提案は3〜7件 | 採用率、人による評価 |
| 分解・要約・生成（AI-03〜05） | 出力の形式が正しい割合100% | 人による評価 |
| 意味の近い検索（AI-06） | 評価セットで、期待するノードが上位5件に入る割合（基準の値はP2で決める） | ― |
| 作業枠の提案（AI-07〜09） | 出力の形式が正しい割合100%。既存の予定や稼働時間との重なり0件。期限を過ぎる枠0件。自然文の日時の解釈が期待と一致する割合（基準の値はP3で決める） | 採用率 |
| 朝のブリーフィング（AI-10） | 出力の形式が正しい割合100%。当日の予定がすべて含まれる | 人による評価 |

## 性能（I-08）

| 目標 | 測り方 | いつ |
| --- | --- | --- |
| NF-01：API応答の95パーセンタイルが300ミリ秒以内（LLMを除く） | 負荷試験のツールで、主要なAPIを測る | 各フェーズの終わり |
| NF-02：500ノードで、操作から画面の反応まで100ミリ秒以内 | 500ノードのデータを使い、Playwrightから操作して測る | P1の終わりから、各フェーズの終わり |
| NF-03：最初の文字が出るまでの時間 | llm\_callsとトレースに記録し、推移を見る | 常に記録する |

結果はリリースノートに残す。

## E2Eのシナリオ（I-03）

主要なユースケースごとに1本以上。すべてのシナリオで、開いた画面にアクセシビリティの自動検査をかける。LLMはモック、GoogleやSlackなどの外部サービスはサーバー側のスタブに差し替える。

| ID | シナリオ | 対応 | フェーズ | 流すとき |
| --- | --- | --- | --- | --- |
| E2E-01 | スモーク：ログイン→マップ作成→ノード追加 | AU-01、MM-01、MM-02 | P1 | PR（必須）、毎晩 |
| E2E-02 | 登録→確認メール→ログイン→ログアウト。パスワード再設定、ログインの試行制限、許可リストにないメールアドレスで登録できないことも確かめる | AU-01、AU-02、AU-06〜08、AU-11 | P1 | 毎晩 |
| E2E-03 | アイデアを広げる：マップ作成→AIの提案→採用→Undo→Redo | UC-01、AI-01、AI-02、MM-07 | P1 | 毎晩 |
| E2E-04 | マップを整理する：ドラッグでの親の付け替え、折りたたみ、再読み込み後も保たれる。P2で検索と要約を足す | UC-02、MM-03、MM-04 | P1、P2 | 毎晩 |
| E2E-05 | 認可：別の利用者でログインし、他人のマップのURLを開いても見えない | AU-03 | P1 | 毎晩 |
| E2E-06 | 枝をタスク化する：ノード→タスク→タスク一覧→元のノードへ | UC-03、TK-01〜04 | P2 | 毎晩 |
| E2E-07 | 予定を一画面で見る：Googleのスタブと同期→カレンダーに予定と作業枠が並ぶ | UC-04、CL-01〜06 | P2 | 毎晩 |
| E2E-08 | 連携の案内：未接続でカレンダーを開くと、理由と接続方法が出る | IN-11、IN-12 | P2 | 毎晩 |
| E2E-09 | 自動で枠を確保する：提案→理由の表示→承認→Googleのスタブに書き込まれる | UC-05、AI-07〜09 | P3 | 毎晩 |
| E2E-10 | 自然文で予定を入れる：一文から枠の提案 | UC-06 | P3 | 毎晩 |
| E2E-11 | マップからカレンダーへ：ノードを時間枠へドラッグし、タスクと作業枠を一度に作る | CL-09 | P3 | 毎晩 |
| E2E-12 | 成功基準の流れ：マップ→AIの提案→タスク化→枠の提案→承認→カレンダーに反映。利用シナリオ例（資格学習）をそのままなぞる | 成功基準 | P3 | 毎晩 |
| E2E-13 | 通知を受け取る：朝のジョブを動かし、Slackのスタブに当日の予定が届く | UC-07、AI-10 | P3 | 毎晩 |
| E2E-14 | Claudeから操作する：個人用トークンで、MCPからマップを参照しノードを足す。画面を使わないので、PlaywrightではなくAPIのシナリオテストで書く | UC-08、IN-06 | P3 | 毎晩 |
| E2E-15 | 履歴とゴミ箱：版を選んで復元する。削除したマップをゴミ箱から戻す | MM-18、MM-19 | PX | 毎晩 |
| E2E-16 | 外部へ書き出す：タスクをNotionやGitHubのスタブに書き出す | UC-09 | P4 | 毎晩 |
