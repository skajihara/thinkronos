# 0034 CIの構成（C-12）

## 状態

承認済み、2026-11-23

## 背景

PRごとに品質を自動で確かめるCIを作る（C-12、I-02、I-07、NF-10、NF-15、NF-16）。アプリのコードがまだ無いので、ジョブの骨組みを先に作り、コードが入った時点でそのまま動く形にする。決める必要があったのは次の4点。

- Pythonの依存管理
- 変更した行のカバレッジの測り方
- 脆弱性検査の道具
- 必須チェックの分け方（スキップされるジョブを必須にしてよいか）

## 比べた選択肢

| 項目 | 案 |
|---|---|
| 依存管理 | uv ／ pip＋requirements.txt（ロックが弱い）／ poetry（Dependabotでは `pip` 扱い） |
| 変更行カバレッジ | pytest-cov ＋ diff-cover ／ Codecov など外部サービス（アカウントとトークンが要る） |
| 脆弱性検査 | Trivy ／ pip-audit ＋ `npm audit`（2つの道具になる） |
| 必須チェック | A: `ci-gate` 1つ ／ B: 全ジョブを個別に必須 ／ C: 骨組みの間は必須にしない |

## 決定

- 依存管理は **uv**（`uv.lock` を正、CIは `uv sync --locked`）。Python 3.13（バックエンドの土台のIssueで確定）。
- 変更行のカバレッジは **pytest-cov ＋ diff-cover**（`--fail-under=80`）。
- 脆弱性検査は **Trivy**（HIGH・CRITICALで失敗）。PRごとと週1回。アクションはタグで固定する。
- 必須チェックは **A**：`ci-gate` と `security-scan`（と既存の `pr-title`、`branch-policy`、`commitlint`）。

## 理由

- GitHubの公式の説明では、ワークフロー全体を `paths:` などのフィルタでスキップすると必須チェックが Pending のまま止まる。ジョブを `if:` でスキップした場合は Success として扱われる。そのため、スキップは job の `if:` で行い、`needs` と `always()` で結果を見る `ci-gate` を必須にする。ジョブが増減してもルールセットを変えずに済む（[Troubleshooting required status checks](https://docs.github.com/en/enterprise-cloud@latest/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks)）。
- Dependabot は `uv` を公式にサポートする（バージョン更新のみ。セキュリティ更新は対象外）。Trivy も `uv.lock` と `package-lock.json` の脆弱性検査に対応する（[Dependabot](https://docs.github.com/en/code-security/reference/supply-chain-security/supported-ecosystems-and-repositories)、[Trivy](https://trivy.dev/docs/dev/coverage/language/)）。
- diff-cover は `--compare-branch` と `--fail-under` を持つ（[PyPI](https://pypi.org/project/diff-cover/)）。

## 影響

- `ci-gate` は、全ジョブがスキップされても成功する。バックエンド・フロントエンドの土台のIssueで、`backend` と `frontend` ジョブが実際に動いていることを確かめる。
- 層の依存に反するimportでCIが失敗することは、対象のコードが無いので**未検証**。バックエンドの土台のIssueで、違反するimportを入れて確かめる。`.importlinter` のパッケージ名（`thinkronos`）も、そのとき合わせる。
- フロントの変更行カバレッジ（Vitestのlcovをdiff-coverに渡す）は未確認。フロントの土台のIssueで確かめる。
- `openapi` ジョブは `make gen-openapi` と、リポジトリ直下の `openapi.json` を前提にする。どちらもバックエンドの土台のIssueで作る。
- Trivyの `--severity` と `--exit-code` の組み合わせは、公式の1ページでは確認できていない（第三者の記事のみ）。実行結果で確かめる。
- スモークE2E（I-07）は、P1で最初のE2Eができてから `e2e-smoke` ジョブとして足し、`ci-gate` の `needs` に加える。
- 対処できない脆弱性は `.trivyignore` に理由つきで書く。
- 検査は依存ライブラリの脆弱性（`scanners: vuln`）に限る。Dockerfile の設定検査（misconfig）を有効にすると、既存の `docker/postgres` と `docker/stub` が DS-0002（rootユーザー）でHIGHとして失敗した（PR #24 の初回実行）。USER の追加はコンテナの動作に関わるので、別Issueで扱う。
- Trivyの `--severity`／`--exit-code` は、上の初回実行で HIGH を検出して失敗することを確かめた。
