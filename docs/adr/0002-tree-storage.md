# 0002 ツリーの保存方式

## 状態

承認済み、2026-11-23（企画書の決定 D-01 を記録したもの）

## 背景

マインドマップのノードは木構造で、親の付け替え（MM-03）、枝ごとの削除（MM-02）、折りたたみ（MM-04）を頻繁に行う。操作ログ（D-02）は1回の移動を1つの操作（`move_node`）として記録し、項目単位の後勝ち（D-13）で並行の変更をまとめる。1つのマップは2,000トピックまで（`docs/guide/map.md`）で、画面はマップを丸ごと読み込む。

## 比べた選択肢

| 案 | 移動の書き込み | 子孫の取得 | 後勝ちとの相性 |
|---|---|---|---|
| 隣接リスト（`parent_id`） | 1行 | 再帰CTE、または全件を読んでアプリで組む | 良い。親は1つの項目 |
| 経路（`ltree`、パス文字列） | 子孫の行をすべて書き換える | 索引で速い | 悪い。1回の移動が多数の行の変更になり、項目単位の後勝ちと衝突する |
| 閉包テーブル | 子孫×先祖の行を作り直す | 索引で速い | 悪い。同上で、行数も増える |
| 入れ子集合 | 多数の行の範囲を書き換える | 速い | 悪い。挿入と移動のたびに広く書き換える |

## 決定

隣接リスト（`nodes.parent_id`）にする。兄弟の順は別の列 `sort_key` で持つ（ADR 0003）。

## 理由

- 移動が1行・1項目の変更で済み、操作ログと項目単位の後勝ち（D-13）にそのまま合う。
- 画面はマップの全ノードを一度に読み込み、木はクライアントで組む。2,000トピックなら全件の読み込みで足り、子孫を索引で引く速さは要らない。
- 循環は、移動の検証でアプリが先祖をたどって防ぐ（D-17）。サーバー側でもマップの全ノードがメモリにあるので、たどる費用は小さい。

## 影響

- 循環の防止は DB の制約では守れない。アプリの検査と、性質ベースのテスト（「どの順で操作を適用しても循環がない」）で守る。
- 枝ごとの削除は、サーバーが子孫を集めて論理削除し、Undo 用に削除前の内容を返す（`.kiro/specs/map/design.md`）。
- 将来、マップをまたいで子孫を検索する機能が要るなら、再帰CTEで足りるかを計測して判断する。
