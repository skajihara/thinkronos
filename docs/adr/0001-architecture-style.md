# 0001 アーキテクチャのスタイル

## 状態

承認済み、2026-11-23（企画書の決定 C-01 を記録したもの）

## 背景

API、ワーカー、定期実行の3つのプロセスが同じ業務ルールを使う（C-01）。外部の依存（PostgreSQL、Ollama、Googleカレンダー、Slack）は、ローカル環境とAWS環境で置き換える（移植性、非機能要件の重視の順）。LLMとGoogleは、テストで本物を呼ばずに確かめたい（I-01）。

## 比べた選択肢

| 案 | 特徴 |
|---|---|
| レイヤード（router → service → repository） | 単純で情報が多い。サービスが ORM や外部SDKの型に直接依存しやすく、置き換えとテストの差し替えが弱い |
| ポート＆アダプター（ヘキサゴナル） | 中心（domain、application）は抽象（ports）だけに依存する。置き換えとテストの偽物が容易。層と組み立ての手間が増える |
| クリーンアーキテクチャ（4層を厳密に） | ポート＆アダプターと考え方は同じ。個人開発の規模では層が多すぎる |

## 決定

ポート＆アダプターを採用する。層は `domain`、`ports`、`application`、`adapters`、`api`、`worker` で、組み立ては `bootstrap.py` だけで行う（構成は ADR 0035）。

## 理由

- Ollama → Bedrock、PostgreSQL → RDS／Aurora、ファイル → S3 の置き換え（P4）を、アダプターの追加だけで行える。
- 単体テストは、ポートの偽物で domain と application を確かめられる。結合テストは、アダプターを本物の PostgreSQL で確かめる（I-01）。
- API・ワーカー・MCP が同じユースケースを使い、業務ルールを二重に書かない（MCP は API を呼ぶだけ、C-22）。

## 影響

- 層の依存の向きは import-linter の契約（7本、`.importlinter`）でCIが止める。
- 1つの機能でファイルが増える。小さな機能でも、ポートとアダプターを分ける手間がかかる。
- 設計のレビューは、カスタムエージェント `design-reviewer` が層の境界を確かめる（G-24）。
