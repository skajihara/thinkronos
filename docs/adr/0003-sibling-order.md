# 0003 兄弟ノードの並び順の表現

## 状態

承認済み、2026-11-23（企画書の決定 D-01、D-17 を記録したもの）

## 背景

兄弟の並べ替えと、兄弟の間への挿入（MM-02、MM-03）を、1つの操作（`create_node` か `move_node`）で表したい。並行の変更（別のタブ、将来の共同編集）で、他の兄弟の行を書き換えずに済む表現が必要（D-13）。

## 比べた選択肢

| 案 | 挿入・並べ替えの書き込み | 並行の変更 |
|---|---|---|
| 整数の連番（position） | 後ろの兄弟をすべて書き換える | 衝突しやすい |
| 間隔を空けた整数・小数 | 普段は1行。間が詰まると振り直す | 振り直しが多数の行の変更になる |
| 分数インデックス（文字列） | 常に1行。前後のキーの間の文字列を作る | 同じ場所への同時の挿入で、同じキーが作られることがある |

## 決定

分数インデックスの文字列 `sort_key` を使う。照合順序は `COLLATE "C"`（バイト順）にする。キーはクライアントが `fractional-indexing-jittered`（CC0）で作り、サーバーは形式と兄弟内の一意だけを確かめる。

## 理由

- 挿入と並べ替えが、常に対象のノード1行の変更で済み、操作ログに合う。
- `COLLATE "C"` にすると、データベースの照合順序（ロケール）によって順番が変わらず、クライアントの文字列比較と一致する。
- ランダムな揺らぎ（jitter）を足すライブラリにすると、2つのタブが同じ場所へ同時に挿入しても、同じキーになることがほぼ無い。

## 影響

- 兄弟内の一意は部分一意索引で守る（`parent_id` が NULL でなく、未削除）。重なったら 409（`/problems/sort-key-conflict`）を返し、クライアントがキーを作り直す。
- 同じ場所への挿入を繰り返すとキーが長くなる。振り直し（rebalance）はしない。長さが問題になったら、計測して判断する。
- 浮いたトピック（MM-12、PX）は親を持たないので、`sort_key` を使わない。
