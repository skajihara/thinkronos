# 0012 マインドマップの描画方式

## 状態

承認済み、2026-11-23

## 背景

マインドマップの描画方式を決める必要があった（B-04）。日本語のインライン編集（IME）、キーボード操作とアクセシビリティ（B-07）、ノードをカレンダーへドラッグする操作（CL-09、R-13）、数百ノードでの速さに効く。

## 比べた選択肢

3方式を同じ21本のPlaywrightテストで比べた（ノード数50と500、Chromium 159、React 19 / Vite）。

1. **React Flow**（`@xyflow/react` 13.0.2、MIT）：ライブラリが描画・パン・ドラッグ・線を担う。
2. **Custom SVG**：ノードも線もSVG。pan/zoomは `d3-zoom`、レイアウトは `d3-hierarchy`（ともにISC）。
3. **Hybrid**：ノードは絶対配置のHTML `div`、つながり線はSVG 1枚、pan/zoomはCSS transform。レイアウトは `d3-hierarchy`。

## 決定

**Hybrid**（ノードはHTML、線はSVG、pan/zoomはCSS transform）を採用する。ノードのドラッグは自前のPointer Eventsで実装する。

## 理由

主要な計測値（中央値。出典は `RESULT.md` の§2、§3、§5）：

| 指標 | React Flow | Custom SVG | Hybrid |
|---|---|---|---|
| 初回描画 50ノード | 79.6 ms | 46.1 ms | 45.8 ms |
| 初回描画 500ノード | 348 ms | 196 ms | 146 ms |
| ノード追加（500ノード時） | 164 ms | 46 ms | 47 ms |
| ドラッグ FPS（CPU 4倍遅） | 49.8 | 52.2 | 60 |
| ドラッグ反応時間（CPU 4倍遅） | 145 ms | 59 ms | 39 ms |
| JS gzip | 166 KB | 96.5 KB | 96.3 KB |
| レンダリング固有のコード | 401行 | 536行 | 502行 |

- 通常条件（CPU制限なし）では、パン・ドラッグは3方式とも60 fpsで差がない。差が出るのはCPUが遅い条件とノード数が多い条件。性能だけでは決め手にならず、Hybridが最も余裕がある、という位置づけ。
- 文字が普通のHTMLなので、`<textarea>` によるインライン編集、IME、`role="treeitem"` / `aria-*` / `tabindex` をそのまま使える。SVGは編集欄に `<foreignObject>` が要る。「SVGのほうがa11yに有利」という当初の推測は、実装すると成り立たなかった。
- ドラッグ中の重なりをCSSの `z-index` で解決できる（SVGにはz-indexがない）。
- ライブラリ依存は `d3-hierarchy`、`d3-zoom` のみ。React Flowは2026-11に13.0.0が出たばかりで、変更への追従コストが見込まれる。
- 実機の日本語IME（Windows、Microsoft IME、Chrome、Hybrid）を2026-11-22に確認し、おおむね問題なし。

React Flowは実装行数が最小で、ズームやミニマップが標準で付く。ノード数が数十で開発速度を最優先するなら有力だが、500ノードでの追加が約160 ms、低速CPUでのドラッグ反応が約145 ms、バンドルが約1.7倍である点を踏まえ、採らなかった。

## 影響

- pan/zoom、ドラッグ、つながり線を自前で保守する。ズームの上限・下限、ピンチ操作、ミニマップは付いてこない。
- 本実装での条件：画面外のノードへフォーカスが移ったときのパン、`aria-live` による追加・移動の通知（B-07）を実装する。
- 試作で未確認の点（本実装で確かめる）：Chromium以外のブラウザ（特にSafariの `foreignObject` とIME）、タッチ操作、500ノードを超える規模（必要なら仮想化）、本番ビルドでの計測、スクリーンリーダーの実機読み上げ。
- 計測はフレーム粒度（約17 ms）の制約があり、±17 ms未満の差は有意としていない。低速CPUはエミュレーション（4倍）による擬似的な条件。
- Custom SVGのドラッグがHybridに届かなかった理由は未調査。
